# Handshake Sync: threat model and failure handling

## Security boundary

The sync design protects data in transit and detects unauthorized changes to accepted log history, assuming each device key remains private and a trusted checkpoint is held somewhere other than the file being checked. It does not prove that a person entered a true statement, that a local clock was correct, or that a local administrator with access to the device cannot erase both a log and its local checkpoints. Signed logs are tamper-evident only once the design in M0.5 ships and devices retain a trusted head/checkpoint.

Use mDNS only to find a possible peer. The QR carries a one-use locator and nonce, not a reusable secret. Authenticate the connection with Noise XX, show the same three-word comparison phrase derived from that handshake on both screens, and pin the peer's identity key only after both people confirm the phrase at the Archive monolith. mDNS service records carry generic protocol/version/port information, not names, entry text, or stable identity. RFC 6762 describes link-local discovery and warns that hostile participants require security above mDNS; local network access also has platform privacy requirements. [RFC 6762 security considerations](https://www.rfc-editor.org/rfc/rfc6762.html#section-11) · [Apple local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy?changes=_9%2C_9) · [Android local network permission](https://developer.android.com/privacy-and-security/local-network-permission?authuser=89)

## STRIDE-style threats

| Threat | Attacker/failure | Impact | Required defense and remaining limit |
|---|---|---|---|
| Spoofing | Host on LAN advertises `_citadel._tcp`, copies a device label, or emits a BLE advertisement | Pairing lure, denial of service, or attempt to receive a bundle | Discovery never authenticates. Require both devices to display and confirm the same Noise transcript phrase, then pin the identity key. Rate-limit prompts; the user can stop discovery. |
| Tampering | Peer changes, truncates, reorders, or injects log events | Journal corruption or a false entry | Per-device signed sequence and previous-hash link; verify identity, signature, sequence, previous hash, and payload before import. Compare peer head/checkpoint. A key compromise or an unanchored whole-log rewrite remains a risk. |
| Repudiation | Device owner later denies authoring an entry | Dispute about authorship | Each entry event is signed by its device key and records author/device and migration provenance. A signature proves key use, not the human's intent or the truth of text. |
| Information disclosure | LAN observer, nearby BLE scanner, lost device, or unencrypted exported bundle | Entry text, device identity, or usage pattern leaks | Noise session encryption for LAN transfer; no journal content in discovery; rotate BLE identifiers and advertise only a generic pairing hint. Encrypt transfer bundles to the paired recipient. At-rest encryption/keychain integration is **UNVERIFIED** and must be decided before release. |
| Denial of service | Malicious peer floods discovery, sends huge/incomplete bundle, or holds a connection open | Pairing unavailable or disk/memory exhaustion | User-initiated, time-limited discovery; cap sizes, timeouts, concurrent sessions, and decompressed data; stream into a bounded temporary area. Do not append until full verification. |
| Elevation of privilege | Stolen paired device uses its valid key or an import parser exploits malformed data | Access to local archive or unauthorized records accepted | Scope keys by device and role; schema-versioned, bounded parser; desktop authority signs revocation events; never execute received payloads. A stolen valid device is trusted until revocation reaches a verifier. |
| Clock manipulation | User or malware moves wall clock or timezone | Misleading display dates or attempted late write | Clock value is descriptive metadata only. Enforce per-device monotonic sequence and sealed day/segment state; do not let a clock change edit or reopen accepted events. Absolute offline civil-time truth cannot be proven. |
| Pairing phrase interception | Observer sees/hears the phrase or tricks user into confirming a different screen | Wrong device is trusted | Compare both screens while physically at the Archive pairing ritual; phrase is handshake confirmation, not a secret/password. Show stable pinned identity fingerprint after initial confirmation; re-pair after identity reset. |

The mDNS and mobile permission details can vary by OS release and target SDK; re-check at implementation time. Android currently documents an opt-in transition for Android 16 and required local-network permission for apps targeting API 37+; exact app behavior is **UNVERIFIED** until the target SDK is selected. ## Entry, segment, and day records

1. Each device owns an Ed25519 signing key. A journal entry is immutable at first save. A correction is another signed entry with a `corrects`/`continues` link; there is no in-place text edit, delete, or retract in the canonical log.
2. Encode a versioned, fixed-schema event deterministically before hashing/signing. Deterministic CBOR is one suitable encoding rule set; the exact Rust encoding crate and canonical-form review are **UNVERIFIED**. [RFC 8949 deterministic encoding](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2)
3. An event contains at minimum: schema version, stable entry/event ID, device ID/public-key fingerprint, device sequence, previous event hash, entry text and tags, immutable entry day ID, local wall time and UTC offset as descriptive fields, hybrid logical clock, provenance/correction links, and signature. The signature covers a domain-separated canonical header and payload hash. The event hash covers those bytes and the signature. Never use a timestamp as an identity or as permission to overwrite another event.
4. Each device emits an immutable `DayClose` event containing that device's final sequence and head hash for its local day segment. The day is globally “converged” only after all writers in the day's fixed roster have supplied a close or an authorized roster change has been recorded. A local sealed segment can be complete while the shared day is still marked “awaiting another device.”
5. Graph triples are a projection of verified events. Rebuilding the graph cannot change or delete a signed entry. Embeddings are computed on each device and are not synchronized.

## Two devices offline across midnight: exact merge result

Assume paired devices A and B have both been authorized for the day's roster. Both edit the same visible Today view, lose connectivity before midnight, and each local midnight passes while both remain offline.

1. **Before disconnection:** A and B each append their own entries locally as immutable signed log events, with different device IDs and increasing per-device sequence numbers. Both entries may describe the same topic; neither changes the other's event. Each local Today projection reads its device's events and any previously accepted peer entries.
2. **A's midnight:** A writes a signed `DayClose(day_id, A.final_sequence, A.head_hash)` after its final entry. A seals only A's day segment, advances its own Today, and rejects later writes into A's sealed segment. No message reaches B.
3. **B's midnight:** B independently writes its own close event with B's final sequence/head, seals B's segment, and advances its own Today. Neither device claims that its local close is a global close.
4. **Reunion and handshake:** devices discover a candidate on LAN or the user selects a local bundle; they run Noise XX, compare the phrase on both screens, confirm the pinned peer identity, then exchange protocol versions, log heads, and Merkle summaries. Discovery does not grant trust.
5. **Diff and verification:** each sends missing log records in bounded chunks. The receiver verifies the pinned signer, schema, signature, previous-hash continuity, sequence, event IDs, and each close's final head. Identical already-present events are idempotent no-ops. Incomplete or invalid chunks stay in temporary/quarantine storage and are not projected.
6. **Union, no winner:** verified events from A and B are unioned by immutable event ID. Since ordinary entries have distinct IDs, both survive. If the same ID arrives with different valid payloads, preserve both candidates in quarantine and show a collision; do not choose one by timestamp or last-write-wins.
7. **Stable display:** render the shared day as the two sealed device segments, ordered by hybrid logical clock and then device-key fingerprint and sequence as a deterministic tie-break. Preserve each original local time and offset beside the entry. This ordering is for display only and does not claim a globally knowable order for simultaneous offline events.
8. **Convergence receipt:** once both roster members' verified `DayClose` events are present, append a new signed merge-manifest event referencing both close heads and the union's resulting head set. Neither original segment nor either close is rewritten. Mark the shared day “converged.”
9. **Late or absent device:** if another roster member has not closed, show “local segment sealed; shared day awaiting device X.” Do not silently claim completeness. The desktop can record an authorized roster/revocation change; the resulting manifest names the change and the heads it accepted.

The Today CRDT is a transport-friendly set/list view over immutable entry IDs, not the authority for entry contents. The signed log and close/merge events are the authority. Automerge is the recommended CRDT candidate in the implementation plan; its exact Rust data model must preserve append-only IDs and collision quarantine.

## Clock skew and travel

- **Day assignment:** at first append, use the active local civil day and timezone offset reported by the device, then persist that day assignment inside the immutable event. The app records both this civil-time claim and an HLC/sequence. HLC communicates causal ordering; it does not certify real-world time. [HLC paper](https://cse.buffalo.edu/~demirbas/publications/hlc.pdf)
- **Timezone travel:** a timezone change affects the displayed local timestamp and the next unsealed day boundary. It never reassigns an existing event. Once a device has emitted a close for a day ID, it cannot reopen that segment after travel.
- **Clock moving backward:** persist a monotonic accepted-day high-water and device sequence. If the OS date regresses behind a sealed day, do not open or append to that sealed day; keep new captures in a clearly labeled current open segment until a later local date catches up or the user resolves the clock warning. Never rewrite event timestamps to hide the discontinuity.
- **Clock jumping forward:** flag the discontinuity and ask the user to confirm advancing/sealing across skipped dates. Do not synthesize empty entries or infer events for skipped days. Once a close is signed, the segment cannot be reopened.
- **Malicious clock:** a device can claim a false civil date while offline. A signature proves that its key signed that claim and sequence, not that the wall clock was accurate. Peer HLCs and sequence numbers prevent a later event from replacing an earlier event but cannot provide trusted absolute time without an online trusted clock, which this design does not use.
- **Ordering:** exchange HLC state during a verified handshake; order concurrent events deterministically by HLC, device key, and sequence. Do not use wall time or last-write-wins to decide authorship, revocation validity, or content.

## Forks, incomplete data, and replay

- **Fork:** two valid children from the same device sequence and previous hash indicate a cloned key, rollback, or device-state fork. Preserve both branches and their source files in quarantine, pause that device's import, and ask the user to choose a recovery lineage. Never select by newest timestamp. A signed fork notice is itself appended; neither branch is erased.
- **Partial transfer:** write into a temporary spool with byte, record-count, and time limits. Resume by verified sequence/hash ranges. Append only after the full chunk set, final head, signatures, and schema validate. A restart discards or resumes only the verified spool; partial bytes are never shown as journal entries.
- **Corrupt bundle:** reject the bundle, retain a local diagnostic/quarantine copy, and leave canonical log and graph untouched. Rebuild the graph only from the existing verified log.
- **Replayed bundle:** identical event ID, hash, signature, and sequence already accepted is a no-op. A sequence collision with a different hash is a fork and follows the quarantine path. A valid older missing event from a still-authorized device can be imported; its old timestamp alone does not make it a replay attack.
- **Bundle confidentiality:** signatures do not encrypt entry text. For USB/AirDrop-style bundles, encrypt to a paired recipient key or a one-time user-transferred key and authenticate the manifest. Candidate AEAD crate `chacha20poly1305` is **UNVERIFIED** for the app's Rust/MSRV/build targets; key exchange and bundle format need a separate review.

## Lost or stolen phone and revocation

- At the desktop Archive monolith, the owner appends a signed revocation event naming the phone key and the roster epoch from which it is excluded. The desktop rejects newly presented events from that key after it has accepted the revocation.
- If the desktop is offline from the LAN, the revocation cannot propagate immediately. It travels only at the next verified local encounter or by carrying a signed local bundle. Every peer must compare revocation heads before accepting new entries. Do not imply remote wipe or instant network-wide revocation.
- Offline peers cannot reliably distinguish a legitimate unsynced entry created before theft from a stolen-device entry created after theft: the device's claimed timestamps are not trusted. After learning of revocation, quarantine all previously unseen events from the revoked key for manual salvage; keep already accepted entries and their signatures, and never silently delete them.
- A user may revoke the desktop authority only with the independent recovery authority. If that recovery authority is also unavailable, peers continue using their last trusted key set and display the stale-revocation state.

## Desktop recovery

At first device enrollment, generate a separate recovery authority and present a local recovery kit. Recommended form: one encrypted recovery file copied to two user-chosen offline locations plus a printed high-entropy recovery code/words kept separately. The exact UX and key derivation are **UNVERIFIED** and need a usability/security review. The kit can authorize a replacement desktop and verify/import device logs; it is not stored with the journal by default. If every recovery copy and the desktop key are lost, identity continuity cannot be recovered cryptographically. The journal can still be imported as an explicitly untrusted archive under a new lineage; old signatures remain attached but cannot be newly vouched for.

## Hostile LAN, mDNS, and BLE privacy

- Treat every discovered peer address, service record, and device label as attacker-controlled input. Bind after user-confirmed Noise transcript phrase; pin the peer identity; re-check authorization and revocations before transfer.
- A spoofed `_citadel._tcp` record can cause a fake prompt or denial of service, but must not yield journal content or pairing without phrase confirmation on both devices. Bind only the selected interface; require explicit local-network permission where the OS asks.
- BLE is a rendezvous hint only. Rotate random advertisement IDs for each brief pairing window; never broadcast a stable device name, account-like identifier, public key, entry text, or history. Stop advertising immediately after connection/timeout. A BLE observer can still notice that a device is nearby during the short window.
- Provide user-visible start, stop, and timeout controls at the Archive monolith. Do not start background discovery at app launch. Manual USB/AirDrop bundles use the same signature, recipient, replay, and revocation validation as LAN transfer.
